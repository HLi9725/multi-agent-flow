# 第四阶段架构技术总结

## 已交付结构

- 4A：本机 STDIO 工具入口，服务端登记项目、有限字段、分页和响应脱敏。未知项目与跨项目访问拒绝。
- 4B：主体与 scope 校验、任务版本与类型锁、持久化幂等、审计链。业务已落盘而审计待补记时明确区分，重试不重复业务。
- 4C：回环 compat HTTP、Bearer、受众和有效期、jti 撤销、限流、超时及副本恢复。未在本批部署公网服务或 TLS。
- 4D：Cursor 真实 STDIO/HTTP 的读取、授权写入、查回、幂等、重启与撤销记录保留。正式用户批准和拒绝走本机可信入口与 Runner.accept/reject，两套确认编号分别绑定，不由模型代签。
- 4E：GitHub 是首个连接器。只读默认，写入须登记开启。外部状态不驱动本地验收，冲突与契约变更不能被投影绕过。

## GitHub 本轮真实问题与修复

测试目标唯一为 `https://github.com/users/HLi9725/projects/2`，私有沙箱 `yy-flow-s4-sandbox`。首次真实循环暴露“成功投影不推进基线”和“applied 动作吞掉新循环”两项 P1。

修复采用字段级已应用确认、独立动作代际、写前持久化、逐项结果保存和项目排他锁。保留原失败账本，不靠删除账本恢复。部分页缓存随游标保留，损坏状态拒绝执行；建卡响应丢失时先认领远程标记，不因可见性延迟重复建卡。

真实复验已覆盖：连续三次状态投影、三轮归档/恢复，以及远程建卡成功后在本地成功标记保存前主动结束进程，新进程恢复认领同一草稿。分页使用真实 51 条数据；50 条夹具已可恢复归档，未永久删除。详见《11-第四阶段GitHub连接器说明》第 9–11 节。

## 仍需保留的边界

1. compat 服务不是官方 MCP SDK 后端，不能用已验证的 compat 冒充 SDK 接入。
2. Cursor 原生角色仍可使用；无法独立核验的原生完成回执不能标为真实 Runner 证据。不可核验交接保持拒绝，不强迫安装 Cursor SDK。
3. 本机控制台输入只能绑定操作系统账号，不能证明同一账号下必然由真人操作。批准演练的实际用户操作与该威胁模型限制同时保留。
4. HTTP 真实客户端已完成 JSON 工具闭环，但旧 D6 要求的真实客户端 SSE 证据尚不能由普通协议测试替代。用户已明确将真实客户端 SSE 留作后续兼容验证，本批不记其通过。撤销后 Cursor 表现为发现失败，不把它改写成客户端已显示 REVOKED 正文。
5. 经典 GitHub project scope 不是单项目隔离权限，唯一沙箱约束不等于令牌仅有该 Project 权限。不得将令牌写进登记或报告。
6. Jira、飞书、新卡片 UI、多组织自助接入、公网生产部署和 TLS 不在本批交付范围。

## 结项判定

最终定向 42 passed、1 skipped；冻结后的全量 882 passed、1 skipped、447.65 秒，exit 0；显式真实沙箱只读 1 passed。全量由主协调者实际执行，独立 QA 核验执行结果与冻结哈希；独立限定复审 PASS。默认全量不访问真实 GitHub，不把模拟与真实证据混用。

总结文档完成不替代阶段门禁。最终结项须将各任务正式验收后运行 `python scripts/check_stage_gate.py --action close --stage Phase-4`，只接受 exit 0。SSE 延期边界已由用户明确确认，其他安全与证据门禁不豁免；不修改旧失败记录。
