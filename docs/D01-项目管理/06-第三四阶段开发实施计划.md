# 第三四阶段开发实施计划

## 1. 结论与本次范围

**本轮交付第三阶段，包含 Lite。依赖顺序仍是 3A 基线 → 3B 规则收敛 → 3C Standard 兼容 → 3D Lite 主交付。第四阶段本轮不做。**

现在的问题不是缺少更多角色，而是同一套规则在不同宿主、执行模式和文档中表达不一致。直接增加六个独立 Skill 和多个远程入口，会放大配置漂移、授权边界和恢复成本。Lite 用来减少不必要的规则和流程，不是可无限延期的可选项。

用户已要求本轮交付第三阶段（含 Lite），不含第四阶段的 MCP、远程服务、外部连接器和 3E Compliance。本文件不再把“先做 Standard、Lite 以后再说”当作范围结论。历史审查基线仍只证明当时已核验的范围，不把尚未验证的能力写成已通过。

原始路线见 [多客户端可信化与生态改造实施方案](../../MULTI_CLIENT_MODERNIZATION_PLAN.zh-CN.md)。其历史基线、验收记录保留不改；第三、四阶段后续开发以本文件经用户确认后的批次为准。原路线中“缺少通用 Production Runner”等表述是历史状态，不能继续作为当前结论。

## 4. 必须统一的概念

三类维度彼此独立，不再用“Cursor 一套、其他平台一套”概括全部机制：

| 维度 | 回答的问题 | 边界 |
| --- | --- | --- |
| 宿主与执行模式 | 谁调度、如何真实调用角色 | 原生对话调度、外部 Production Runner 分开验证，不同时调度同一任务 |
| 任务分类/风险 | 做什么、风险多大 | 沿用现有任务分类；不能仅按文件数量判断风险 |
| Workflow Profile | 需要哪些独立检查 | Lite、Standard、Compliance；与宿主托管角色配置分离 |

八个业务角色是可选职责集合，不是每个任务必须串行经过八个人。三个 Runner 托管角色是执行配置，不是新的业务角色。角色显示名称可保留，持久化契约使用稳定角色 ID。

原生模式和 Runner 共用任务、状态、授权及证据语义，但不要求共用全部调用代码。宿主缺少独立子代理能力时必须说明限制，不得以同一窗口自述模拟独立审查。

跨前后端总计划可管理两个子项目，但每个执行任务必须绑定自己的仓库根目录、分支和候选。第三阶段不承诺跨两个 Git 仓库的原子提交、回滚或统一 SHA。

## 5. 第三阶段：分批实施

### 3A：建立可复现基线与预检

目标：后续改造不重新引入已有恢复、协议、路径和 Windows 问题。

- 输出宿主能力矩阵：原生/外部、实际版本、验证时间、证据位置、未支持能力。
- 预检项目根、嵌套仓库、依赖解释器、测试命令、预算和运行锁；不得为预检全盘搜索用户目录。
- 补齐 Maven/多子项目识别；未知技术栈要求明确选择，不自动执行猜测命令。
- 将历史故障转换为脱敏 fixture：503、超时、权限拒绝、输出截断、字段变体、编码错误、数据库 fixture 失败、未提交的部分 Builder 改动。
- 明确错误类型及恢复策略：业务失败交回开发；暂态宿主错误有界退避；权限/认证错误等待授权；协议错误不能伪造业务 FAIL 或 PASS。

验收：

- 3A-01：当前定向测试和全量仓库测试通过，记录跳过原因与环境。
- 3A-02：错误注入均进入预期状态，不能吞掉失败、无限重试或重置历史预算。
- 3A-03：多仓库/未知栈识别失败时零业务写入，错误信息可定位。
- 3A-04：真实支持的模式分别完成一次成功、一次退回修复、一次中断恢复；无法访问的宿主标记未验证，不假定通过。

### 3B：收敛规则与按需上下文

保留一个公开 yy-flow 入口。先在包内拆分 router/task/review/qa/release/admin 模块，不立即要求用户安装六个相互依赖的 Skill。

- 建立“公共安全规则 + 角色职责差异 + 宿主能力差异”的唯一来源。
- 根据任务加载相关模块；选中的规则必须完整读取，不以 token 优化为由截断安全约束。
- 导出 Cursor/Codex/Antigravity 对应文件，产物带源版本；安装和同步校验生成结果。
- 硬编码状态、角色权限和 CLI 默认类型与任务记录之间的差异必须检测，而非静默覆盖。
- 不支持动态加载的宿主使用静态包，行为和门禁保持一致。

验收：3B-01 导出可重复且无漂移；3B-02 所有入口对同一任务给出一致权限与状态；3B-03 安全规则缺失时拒绝启动；3B-04 上下文大小有测量，但不把 token 降低作为牺牲质量的理由。

### 3C：先落地显式 Standard Profile

默认保持现有 Builder → Reviewer → 受控测试 → QA → EvidenceGate → 用户验收路径，先不改变业务阶段数量。

- 工作流策略包含 profile_id、profile_version、必要角色、门禁和预算策略。
- 任务创建后固化有效策略；恢复校验候选、需求/验收契约和策略版本。
- 历史任务仅在能证明旧语义等价时补记 Standard；无法证明时输出差异，不覆盖旧快照或 Evidence。
- Profile 升级需核对新增检查，降级需明确授权；不得用降级消除已存在缺陷。
- 新候选必须重新获得适用的审查/测试证据；旧候选证据不能转绑。

验收：3C-01 无配置的旧入口行为与 Standard 等价；3C-02 策略篡改/不兼容变更被拒绝；3C-03 恢复既不重复已完成阶段也不跳过失效检查；3C-04 原生与 Runner 的 Standard 门禁语义一致。

3A～3C 是 Lite 的依赖，不是用来延期 Lite 的理由。

### 3D：Lite Profile（第三阶段主交付）

面向按内容判定为低风险的代码任务。文档等低风险任务在秘密扫描和文档元数据/路径约束通过后走短链。认证、权限、资金、隐私、数据库迁移和生产部署不允许因项目小、文件少、标题、标签或用户声称而自动选 Lite。风险依据实际 diff 与文件内容。

Lite 使用 Builder + 独立 Verifier + 用户，不伪造 Reviewer/QA 两份证据。必须定义真实 Verifier 报告、允许的状态路径和专属 EvidenceGate，并保留受控检查。风险升级立即停止轻量路径并重新计划。

验收：3D-01 高风险任务不能误选；3D-02 Verifier 与 Builder 调用可区分；3D-03 无证据/失败不能完成；3D-04 Lite/Standard 相互恢复不混用报告。

### 3E：可选 Compliance Profile

在 Standard 上按风险增加架构、安全、部署审批和保留策略，不是机械调用所有八个角色。审批必须绑定真实用户/服务主体；模型不能自称用户完成验收。权限、签名/来源验证、审计保留期限和敏感数据处理必须有明确配置。

验收：3E-01 必需审批缺失不能推进；3E-02 同一模型切换称谓不能代替独立审批；3E-03 审计记录与候选、策略绑定；3E-04 权限变化后旧授权不会继续生效。

### 3F：效果评估与灰度

使用固定脱敏任务集，至少包含文档、小功能、跨模块、迁移、高风险权限、失败恢复六类。先做每类三次 Standard 基线；Lite 只比较适用任务，Compliance 只比较高风险任务，不机械组合所有平台和角色。

记录：实际完成率、首次通过率、缺陷漏检、人工介入原因、有效重试、墙钟时间、可获得的 token/成本。未知 token 写 N/A；模型、宿主版本和输入必须记录。

发布硬门槛：预设安全负例零错误放行；状态/证据一致性测试全通过；支持模式真实恢复通过。性能和完成率用小样本报告，不将三次重复解释为统计保证。若质量下降，关闭新 Profile，保持旧 Standard 可用。

## 6. 第四阶段：先协议，再远程，再生态

### 4A：本地只读 MCP 最小闭环

先从现有领域服务暴露 get_project/get_task/list_tasks/status 等只读接口，使用 STDIO 进行本地试点。工具层不另写一套状态机。

项目由服务端登记 ID 映射，不接受模型传入任意本地绝对路径。对结果做分页、长度限制和脱敏；只读接口也要防止跨项目数据读取。

验收：工具 schema 与错误码稳定；未知项目拒绝；大列表分页不漏项；敏感变量、私有文件不进入响应。此批可独立交付，不等待远程 UI。

### 4B：受控写入与一致性

再开放 create_task、submit_evidence、transition_task、request_acceptance、soft_delete/restore 等必要能力。

- 请求必须校验主体、项目权限、预期任务版本和幂等键。
- submit_evidence 接收数据不等于认可证据。普通客户端不能仅上传 decision=PASS 就推进完成；需可信执行来源、候选和契约绑定，并经过服务端门禁。
- 用户验收是独立授权动作，不能被通用 transition 参数冒充。
- 状态和审计写入原子一致；远程通知采用可重试事件投递，不能先通知成功后丢失状态。
- 超时后查询幂等结果再重试，禁止重复建卡/重复迁移。

验收：越权、重放、并发更新、响应丢失、服务重启和重复 Evidence 均有负向测试；错误返回不泄露凭据。

### 4C：远程部署与认证

先交付单组织、项目隔离的远程部署，再按实际需求扩展多租户。选用受支持的 Streamable HTTP、TLS 和客户端适配的认证方式；协议/SDK 版本在实施时锁定。

认证主体来自可信请求上下文，不信任模型填写的 user_id/tenant_id。细化只读、提交证据、推进任务、验收、管理权限；验证 token 的受众、有效期和权限。禁止任意 shell、路径和跨租户对象引用。

补齐数据库事务、迁移、审计、备份恢复、限流、超时、容量监控和撤销授权。远程服务不能假定可访问用户本机仓库；本地执行器通过明确授权边界上传证据。

验收：跨项目/跨租户隔离、撤销、恢复演练、并发幂等、审计完整性全部通过；部署手册说明数据存储位置与保留策略。

### 4D：客户端接入与可选 UI

先验证目标客户端实际允许的 MCP 接入、认证和写入确认方式，再决定 ChatGPT/其他客户端具体交互。平台支持不以产品名称或历史截图推断。

必须用实际客户端完成“读取任务 → 授权写入 → 查回结果 → 撤销权限”闭环。卡片 UI 是可选增强，不与核心服务发布捆绑；无 UI 时保留结构化文本。Cursor 原生工作流不因没有外部 SDK 而被强制停用。

### 4E：连接器按一个一个交付

首选 GitHub Projects，只读对齐后才开放受控写入；Jira/飞书随后独立排期。保留现有 Adapter，补齐完整分页、错误类型、身份映射、令牌最小权限和同步冲突规则。

YY-Flow 负责执行状态与 Evidence，外部看板作为投影时不能反向绕过验收。若允许外部修改需求，则生成契约变更流程，而非静默覆盖运行中任务。软删除、归档、恢复在不同平台语义不同时需显式映射。

验收：超过一页数据、字段缺失、无权限、速率限制、重复 webhook、乱序事件、双向冲突及部分写失败均能恢复；先沙箱测试，不用真实生产看板做破坏演练。

## 7. 所有批次共用的防错边界

1. **协议**：短结构化结论与大证据分离；引用绑定内容摘要及候选；有长度预算与截断诊断。格式修复不能补造未返回的 PASS、AC 或证据。
2. **权限**：最小作用域授权，精确文件/工具边界；只对必要操作申请权限，不靠全局放行解决设计问题。
3. **重试**：区分业务、协议、暂态宿主、权限和预算；退避有上限，恢复不清零历史；不得承诺永不中断。
4. **测试失败分类**：数据库未知列、缺少导入、fixture 逻辑错误不能一律当环境错误暂停；不确定分类保留诊断供判断，不能误报成功。
5. **缓存**：绑定候选、契约、命令、解释器/依赖与相关环境指纹；远程数据库状态变化需失效策略，不能仅凭 SHA 无限复用。
6. **输出安全**：Windows 编码、异常链、SQLAlchemy URL、pytest locals、日志和模型输出统一脱敏；最终 JSON 输出失败不能破坏已持久化状态。
7. **持久化**：Checkpoint、看板和 Evidence 的断点恢复有一致性检查；历史 session/invocation 不置空；恢复不能凭看板独自跳阶段。
8. **进程**：真实锁判断、子进程清理和超时可观测；心跳不等于模型正在改代码。
9. **迁移**：旧记录只做可证明兼容的升级，保留原始快照和记录；不得为了单任务通关放宽全部任务。
10. **人工边界**：正常缺陷应自动修复闭环；真实缺少权限、资源、必要决策或预算耗尽仍必须暂停。最终用户验收不由模型代签。
